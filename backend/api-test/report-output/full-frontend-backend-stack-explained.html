RoomEase Frontend + Backend Stack Explained (Beginner Friendly)

Technical Summary Paragraph

RoomEase is a client-server mobile app where Flutter (frontend) handles UI and local state, while a Go (Gin) backend handles business logic, database access, and security checks. Firebase Authentication is used for identity proof (Google/email login), then the backend creates its own session_id cookie for protected API access. PostgreSQL (Supabase/local) stores persistent app data, and GORM is the ORM that maps Go structs to database tables and runs migrations. CORS is configured in Gin middleware to allow app/web origins and cookies, and request flow is organized through handlers, services, and middleware.

1. What is frontend vs backend in this project?

  1. Frontend (Flutter, Dart): - Renders screens, dialogs, forms, charts. - Sends HTTP requests using dio. - Stores cookies locally using cookie_jar + dio_cookie_manager. - Manages app state via Providers and services.

  2. Backend (Go, Gin): - Exposes REST APIs under /api/.... - Verifies login token, creates/validates sessions. - Runs business logic (expenses, balances, roomspaces, analytics, recurring). - Reads/writes PostgreSQL through GORM.

2. Request lifecycle (simple mental model)

  1. Flutter screen calls ApiService method.
  2. ApiService sends HTTP request to backend base URL.
  3. Gin router matches endpoint in backend/main.go.
  4. Middleware runs first (CORS, logging, auth, membership checks).
  5. Handler executes endpoint logic.
  6. Handler calls service/database methods.
  7. GORM executes SQL on PostgreSQL.
  8. Response JSON returns to Flutter.
  9. Flutter updates UI/state.

3. Flutter side: how backend is connected

Main connector file: - lib/services/api_service.dart

Key points: 1. Uses Dio(BaseOptions(...)) with base URL from AppConstants.backendBaseUrl. 2. Adds CookieManager so backend session cookies persist. 3. Adds interceptors for: - request/response logging - error handling - ban detection and auto-handling 4. Login call: - POST /api/auth/login with { firebase_token: ... }. 5. After login, all protected APIs rely on cookie session (session_id).

Why this matters: - Frontend does not attach a JWT header for every API. - Backend uses cookie-based session auth after login.

4. Gin (Go web framework) in this project

Main file: - backend/main.go

What Gin is doing here: 1. Creates router with gin.Default(). 2. Registers middleware globally: - CORSMiddleware - LoggerMiddleware 3. Defines public routes (example: /api/auth/login, /api/admin/...). 4. Defines protected group: - protected := router.Group("/api") - protected.Use(middleware.AuthMiddleware()) 5. Adds feature-specific routes (roomspaces, expenses, analytics, recurring, etc.).

5. CORS explained with your code

File: - backend/middleware/cors.go

What CORS means: - Browser security rule controlling which origins can call your backend.

Your implementation: 1. Uses github.com/gin-contrib/cors. 2. Allows empty Origin (important for many mobile app calls). 3. Allows local/dev origins (localhost, 127.0.0.1, 192.168.x.x, etc.). 4. AllowCredentials: true so cookies can be used. 5. Allows common methods and headers.

Why supervisor may ask this: - Cookie-based auth + web requires correct CORS and credentials behavior.

6. GORM explained with your code

Files: - backend/config/postgres.go - backend/services/postgres.go - backend/models/*.go

What GORM does: 1. Connects to PostgreSQL: gorm.Open(postgres.Open(dsn), &gorm.Config{}). 2. Maps structs to tables using model tags. 3. Lets you query with chain methods (Where, Find, Preload, Count, etc.). 4. Runs schema migration via AutoMigrate().

Your AutoMigrate flow: - PostgresService.AutoMigrate() calls config.DB.AutoMigrate(...) with model list. - Also performs post-migrate fixes (invite code generation, QR column backfill).

7. PostgreSQL connection and environments

File: - backend/config/postgres.go

Behavior: 1. Reads POSTGRES_DATABASE_URL from env/config. 2. If Supabase URL: - enforces sslmode=require - adds connection query tuning params 3. If local DB: - uses sslmode=disable 4. Configures pool: - SetMaxOpenConns(10) - SetMaxIdleConns(5) - SetConnMaxLifetime(5m)

8. Authentication architecture (quick)

  1. User signs in with Firebase on Flutter.
  2. Flutter sends Firebase ID token to backend /api/auth/login.
  3. Backend verifies token via Firebase Admin SDK.
  4. Backend creates in-memory session and sets session_id HttpOnly cookie.
  5. Protected APIs are validated by AuthMiddleware.

Important: - Session store is in-memory (services/session.go), so restart clears sessions.

9. Middleware chain and responsibilities

  1. CORSMiddleware - cross-origin rules + credentials

  2. LoggerMiddleware - request/response logs with duration and status

  3. AuthMiddleware (protected routes) - read session_id - validate session - check ban status from users.is_banned - attach user_id to request context

  4. ValidateRoomspaceMembership (roomspace scoped routes) - verifies user belongs to target roomspace

10. Project architecture pattern in backend

Pattern used: 1. Handler layer: HTTP input/output (backend/handlers/*) 2. Service layer: business/database logic (backend/services/*) 3. Model layer: schema structs (backend/models/*) 4. Middleware layer: cross-cutting concerns (backend/middleware/*)

This separation is good for testing and maintenance.

11. Important practical caveats (supervisor-friendly honesty)

  1. Admin routes are currently public in main.go (/api/admin/* has no auth guard yet).
  2. Session store is in-memory, not Redis/DB-backed.
  3. Some analytics endpoints rely on external ML bridge and can fail independently.
  4. Mobile CORS behavior differs from browser behavior; empty origin allowance helps mobile clients.

12. One-line summary

Flutter calls Gin APIs through Dio; Gin uses middleware + handlers + services; GORM maps Go models to PostgreSQL; Firebase proves identity once, then backend cookie sessions secure all protected operations.
