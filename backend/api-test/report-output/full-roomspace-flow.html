RoomEase Full Roomspace Flow (A to Z)

Technical Summary Paragraph

Roomspace in RoomEase is implemented as a membership-scoped collaboration context where every shared operation (expenses, balances, analytics, notifications, recurring templates) is constrained by roomspace identity and validated member access. The Flutter app maintains an active roomspace state (or personal-space null context) via RoomspaceProvider, with cache-first + network-refresh behavior and persisted last selection per Firebase user. On the backend, Gin middleware enforces authentication and roomspace membership checks, while PostgresService owns roomspace lifecycle rules (create/join/leave/remove/process join requests/ownership transfer). Join flow is approval-based using join_requests and notifications, and leave flow includes creator handoff or room deletion logic. In effect, roomspace acts as the core authorization boundary and tenancy unit for shared household data.

1. What a Roomspace is in this codebase

A roomspace is a shared tenant-like container for group expense data.

Primary entities: - roomspaces (backend/models/roomspace.go) - roomspace_members (backend/models/roomspace_member.go) - join_requests (backend/models/join_request.go)

Key properties: - roomspaces.id is UUID - invite_code is unique 8-char code - creator tracked by creator_id (Firebase UID) - active membership tracked in roomspace_members - approval queue managed via join_requests

4. Core roomspace lifecycle flow

4.1 Create roomspace

Frontend: - Calls SmartApiService.createRoomspace(...) -> backend /api/roomspaces.

Backend: - RoomspaceHandler.CreateRoomspace uses authenticated user_id as creator. - PostgresService.CreateRoomspace: - checks subscription-based roomspace limit - generates unique invite code - creates roomspace record - creates creator membership row with role creator

Result: - Creator becomes active member immediately.

4.2 List roomspaces for current user

Frontend: - RoomspaceProvider.loadRoomspaces() fetches and caches list.

Backend: - RoomspaceHandler.GetRoomspaces - PostgresService.GetUserRoomspaces(userUID) joins roomspace_members with is_active=true.

Result: - User sees only roomspaces where they are active member.

4.3 Search and request join by invite code

Frontend: - search code -> /api/roomspaces/code/:code - join-by-code -> /api/roomspaces/code/:code/join

Backend: - SearchRoomspaceByCode validates existence. - JoinRoomspaceByCode creates join request (not direct join). - PostgresService.CreateJoinRequest prevents: - duplicate pending request - joining if already member - joining beyond roomspace limit

Result: - Pending approval workflow starts.

4.4 Process join request (approve/reject)

Frontend: - Notification screen calls /api/join-requests/:id/process.

Backend: - NotificationHandler.ProcessJoinRequest - PostgresService.ProcessJoinRequest transaction: - validates request is pending - validates processor is roomspace member - if accept: adds requester to roomspace_members - sets processed metadata - Sends notifications to requester, processor, and other members.

Result: - Accepted user becomes active member and should then receive roomspace in list.

4.5 Leave roomspace

Frontend: - RoomspaceProvider.leaveRoomspace(roomspaceId)

Backend: - RoomspaceHandler.LeaveRoomspace - PostgresService.LeaveRoomspace

Leave behavior includes ownership handling: - non-creator leaves: membership removal/deactivation - creator leaves: - transfer ownership to suitable member if possible - or delete roomspace if no members remain (as per service rules)

Response includes: - ownership_transferred - new_creator_id - roomspace_deleted

4.6 Remove another member

Frontend: - remove member call from roomspace details screen

Backend: - RoomspaceHandler.RemoveMember - PostgresService.RemoveMemberFromRoomspace

Rules: - only creator can remove members - creator cannot remove themselves via this route

Notifications are sent to removed member + creator.

5. Authorization and access control model

Authentication layer

  • Protected routes require valid session_id cookie (AuthMiddleware).

Roomspace authorization layer

  • ValidateRoomspaceMembership() middleware checks:
  • URL param :id or query roomspace_id
  • user must be active member of target roomspace
  • if not member -> 403 forbidden

This is the key guard that prevents cross-roomspace data access.

6. Frontend state model and UX logic

RoomspaceProvider behavior: - keeps _roomspaces list and _activeRoomspace - supports personal space when _activeRoomspace == null - persistent key is user-scoped: active_roomspace_id_<firebaseUid> - loads cache first, then network (force/non-force refresh) - includes retries for transient network failures

RoomspaceRouter behavior: - if user has roomspaces -> roomspace details - if no roomspaces but pending join request -> pending state screen - else -> roomspace selection/personal space

7. Caching and refresh behavior

Frontend caching: - roomspace data cached via provider + shared prefs - Smart API layer has cache + stale fallback

Live refresh sources: - manual pull-to-refresh / screen refresh - provider refreshRoomspaces() - app lifecycle resume refresh (added in main navigation) - join-request event-driven refresh hooks (where wired)

8. Roomspace-related APIs (current)

Publicly relevant protected APIs: - GET /api/roomspaces - POST /api/roomspaces - GET /api/roomspaces/:id - POST /api/roomspaces/:id/join - POST /api/roomspaces/:id/leave - GET /api/roomspaces/code/:code - POST /api/roomspaces/code/:code/join - DELETE /api/roomspaces/:id/members - GET /api/join-requests - GET /api/join-requests/pending - POST /api/join-requests/:id/process - GET /api/user/roomspaces/count

9. Roles and statuses used

Roomspace member roles (roomspace_member.go): - creator - admin - member - pending

Join request statuses (join_request.go): - pending - approved - rejected - expired - cancelled

10. How roomspace ties to the rest of app

Most shared endpoints and computations are roomspace-scoped: - expenses - balances / settlements - analytics - recurring shared templates - payment confirmation flows

Each of these typically requires: 1. authenticated session 2. membership check on roomspace ID

That makes roomspace the central data partition boundary.

11. Practical caveats and implementation notes

  1. roomspace_members.is_active is critical for effective membership; queries rely on it.
  2. Active roomspace selection is persisted per Firebase user, which avoids cross-user mix-up on same device.
  3. If backend session expires/restarts, frontend may show cached roomspace until next auth refresh.
  4. Join acceptance visibility depends on timely refresh/events; periodic refresh reduces need for relogin.
  5. Legacy RoomspaceService has int-based join helper; current backend IDs are UUID-based and SmartApi paths are the main path now.

12. Exact Frontend-to-Backend Method Mapping (Roomspace)

Core frontend methods that call backend:

  1. Load user roomspaces: - RoomspaceProvider.loadRoomspaces() - SmartApiService.getRoomspaces(...) - ApiService.getRoomspaces() - Endpoint: GET /api/roomspaces

  2. Create roomspace: - UI create action -> SmartApiService.createRoomspace(name, description) - ApiService.createRoomspace(...) - Endpoint: POST /api/roomspaces

  3. Search by invite code: - SmartApiService.searchRoomspaceByCode(code) - ApiService.searchRoomspaceByCode(code) - Endpoint: GET /api/roomspaces/code/:code

  4. Request join by invite code: - SmartApiService.joinRoomspaceByCode(code) - ApiService.joinRoomspaceByCode(code) - Endpoint: POST /api/roomspaces/code/:code/join

  5. Leave roomspace: - RoomspaceProvider.leaveRoomspace(roomspaceId) - SmartApiService.leaveRoomspace(roomspaceId) - ApiService.leaveRoomspace(roomspaceId) - Endpoint: POST /api/roomspaces/:id/leave

  6. Remove member: - SmartApiService.removeMemberFromRoomspace(roomspaceId, memberUid) - ApiService.removeMemberFromRoomspace(...) - Endpoint: DELETE /api/roomspaces/:id/members

  7. Join request inbox + process: - ApiService.getJoinRequests() -> GET /api/join-requests - ApiService.getPendingJoinRequest() -> GET /api/join-requests/pending - ApiService.processJoinRequest(id, accept) -> POST /api/join-requests/:id/process

Backend handlers receiving these: - RoomspaceHandler methods in backend/handlers/roomspace.go - NotificationHandler.GetJoinRequests, .GetPendingJoinRequest, .ProcessJoinRequest in backend/handlers/notification.go

Authorization bridge for frontend-backend connection: - all roomspace APIs are under protected /api group - request must include valid session_id cookie - middleware path: - AuthMiddleware validates session - ValidateRoomspaceMembership validates membership for roomspace-scoped routes

13. One-line summary

Roomspace logic is a UUID-based, membership-gated shared context where join requests control entry, middleware enforces access, and provider state/caching controls active-room UX across the app.

14. Database Tables Used (Roomspace)

Primary tables:

  1. roomspaces - Purpose: canonical roomspace entity (id, name, invite_code, creator_id, lifecycle fields)

  2. roomspace_members - Purpose: membership and role mapping (creator/admin/member, active state, invited_by) - Core authorization table for roomspace access

  3. join_requests - Purpose: approval workflow for invite-code join requests (pending/approved/rejected/expired)

  4. notifications - Purpose: user-facing events for join requests processed, member actions, reminders

  5. users - Purpose: identity/profile source for names and metadata used in roomspace responses/notifications

Related tables touched indirectly by roomspace-scoped pages: - expenses, expense_splits, settlements, user_balances, recurring_expense_templates, recurring_expense_notifications - Reason: many roomspace screens aggregate shared data beyond membership metadata.
