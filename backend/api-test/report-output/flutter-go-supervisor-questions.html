High-Probability Supervisor Questions (Flutter + Go Gin + GORM)

This is a viva-style question bank with concise model answers aligned to your RoomEase implementation.

A. Architecture and design

  1. Q: Why did you choose Flutter for frontend? A: Single codebase for Android/iOS, fast UI iteration, rich widget ecosystem, strong async networking, and predictable state management with Provider.

  2. Q: Why Go + Gin for backend? A: Go gives low-latency concurrency and simple deployment; Gin adds lightweight high-performance routing and middleware support.

  3. Q: Why separate handler and service layers? A: Handlers manage HTTP concerns, services manage business logic and DB operations. This keeps code testable and maintainable.

  4. Q: Explain your end-to-end request path. A: Flutter UI -> ApiService (Dio) -> Gin route -> middleware chain -> handler -> service -> GORM/Postgres -> JSON response -> UI update.

B. Auth and security

  1. Q: Do you use JWT everywhere? A: Firebase ID token (JWT) is used at login only. After verification, backend issues cookie session (session_id) used for protected APIs.

  2. Q: How is login verified? A: Backend verifies Firebase token via Firebase Admin SDK, finds/creates PostgreSQL user, creates session in session store, sets HttpOnly cookie.

  3. Q: What middleware secures APIs? A: AuthMiddleware validates session cookie and checks ban status before passing request to protected handlers.

  4. Q: How is banned user enforced? A: users.is_banned is checked in middleware. If banned, session is deleted and API returns forbidden with logout-required semantics.

  5. Q: Is session storage persistent? A: Current implementation uses in-memory sessions (InMemorySessionStore), so sessions reset on server restart.

  6. Q: How do you handle unauthorized errors in app? A: Dio interceptor catches 401, clears cookies, signs out Firebase user, and redirects auth flow.

C. CORS and networking

  1. Q: Why do you need CORS if app is mobile? A: Web builds and browser contexts need CORS. Also consistent API behavior is maintained across platforms.

  2. Q: Why AllowCredentials=true in CORS? A: Required because auth after login relies on cookies.

  3. Q: Why allow empty origin? A: Many mobile requests do not carry browser-style Origin header, so allowing empty origin prevents false rejection.

  4. Q: How does Flutter persist backend auth state? A: dio_cookie_manager + PersistCookieJar stores session cookies across app restarts.

D. Database and GORM

  1. Q: Why GORM? A: Faster CRUD development, model-based schema mapping, query building, Preload for relations, and migration support.

  2. Q: How do migrations run? A: On backend startup through PostgresService.AutoMigrate() unless skipped via env flag.

  3. Q: What DB is used? A: PostgreSQL (Supabase in cloud; local Postgres for development/testing).

  4. Q: What is the role of PostgreSQL in auth? A: Stores user profile/domain state and ban flags; identity proof itself is by Firebase.

  5. Q: How is DB connection tuned? A: Connection pooling (max open, max idle, conn max lifetime) configured in config/postgres.go.

E. Roomspace and authorization boundary

  1. Q: What is a roomspace technically? A: A shared tenancy boundary. Shared expenses, balances, and settlements are scoped by roomspace_id.

  2. Q: How do you prevent cross-room data access? A: ValidateRoomspaceMembership() middleware validates active membership before roomspace-scoped handlers execute.

  3. Q: How is join flow controlled? A: Invite-code join creates join_requests pending approval. Approved request activates membership in roomspace_members.

F. Expense, split, and balance

  1. Q: How are splits stored? A: Parent expense in expenses; participant obligations in expense_splits.

  2. Q: Where is net balance logic handled? A: Balance service computes net per user and settlement suggestions for roomspace members.

  3. Q: Why can “you owe” and “you get back” both appear in pairwise mode? A: Pairwise obligations can offset across different members; global net mode simplifies to final net settlements.

G. Recurring and notifications

  1. Q: Is recurring auto-added without user action? A: Current product logic uses notifications for due events; user can re-add/cancel through notification processing flow.

  2. Q: Where are recurring templates/notifications stored? A: recurring_expense_templates and recurring_expense_notifications.

  3. Q: How are reminders rate-limited? A: Backend reminder endpoint enforces limit behavior (e.g., 429 handling), and UI should map it to “limit reached” message.

H. Analytics and ML bridge

  1. Q: Why do some analytics APIs return fallback values? A: Core summary can still be computed from DB while external ML endpoints (predictions/recommendations/anomalies) may be unavailable.

  2. Q: What is the ML bridge relationship? A: Backend calls separate ML service; if unreachable/errors, app should show graceful fallback/retry messaging.

I. Admin and moderation

  1. Q: How does ban work end-to-end? A: Admin API updates users.is_banned, ban_reason, banned_at; middleware blocks subsequent protected calls and invalidates session.

  2. Q: Any security risk in admin today? A: Yes. In current main.go, /api/admin/* routes are public; production should protect them with admin auth/role checks.

J. Testing and production readiness

  1. Q: How did you test backend modules? A: Go tests for handlers/services/middleware/models plus API collection tests; DB-backed tests for realistic behavior.

  2. Q: What would you improve before production? A: Secure admin routes, move sessions to Redis/DB, harden observability, and add stricter permission checks/audit logs.

  3. Q: Why not only Firebase and no backend session? A: Backend session simplifies server-side control (ban invalidation, cookie middleware, centralized authorization).

K. Quick rapid-fire one-liners

  1. Q: ORM full form? A: Object-Relational Mapping.

  2. Q: CORS full form? A: Cross-Origin Resource Sharing.

  3. Q: Gin’s role? A: HTTP routing + middleware framework.

  4. Q: Dio’s role? A: Flutter HTTP client with interceptors and timeout controls.

  5. Q: Why Preload in GORM? A: Eager-load relations to avoid manual multi-query mapping in handlers.

M. Flutter frontend deep-dive questions

  1. Q: Why use Provider here instead of setState everywhere? A: Provider centralizes shared app state (roomspace selection, subscription, cached data) and avoids prop-drilling across screens.

  2. Q: How do you avoid stale UI after navigation? A: Key screens trigger refresh on return, and some flows use real-time/event streams plus smart cache invalidation.

  3. Q: How is offline behavior handled? A: App uses cache-first fetch in smart services; when network fails, cached values are shown with sync/retry behavior.

  4. Q: Where is API timeout configured? A: In ApiService via Dio connectTimeout, receiveTimeout, and sendTimeout.

  5. Q: How do you handle global API errors in Flutter? A: Dio interceptors normalize logging and centralize 401/403/ban/session handling.

  6. Q: Why use dialogs heavily (add/edit/recurring/details)? A: Dialogs keep users in context on dashboard/expense screens and reduce navigation complexity.

  7. Q: How does roomspace selection persist between logins? A: Roomspace provider persists last active roomspace key scoped by Firebase user ID.

  8. Q: What causes null-check operator crash in edit flow typically? A: Missing required payload for edit mode (e.g., absent model fields/splits/payer config) or reusing add-flow state without null guards.

  9. Q: How are permission prompts handled? A: First-time permissions dialog asks notification and SMS-related permissions for payment detection features.

  10. Q: Is UI currency consistent? A: Should be Rs.; if $ appears it is a formatting bug in display components.

N. Go + Gin backend deep-dive questions

  1. Q: Why gin.Default()? A: It bootstraps Gin with common middleware and router setup quickly; project then adds custom CORS/logging middleware.

  2. Q: Why group protected routes under /api with middleware? A: It avoids repeating auth checks per route and keeps access control consistent.

  3. Q: What does context enrichment mean in middleware? A: Middleware sets user_id, email, session_id in Gin context so handlers can trust and use authenticated identity.

  4. Q: Why not call DB directly in every handler? A: Service layer reduces duplication and keeps business rules testable independent of HTTP transport.

  5. Q: What is a transaction and where useful here? A: Transaction ensures multi-step DB changes succeed/fail together (e.g., roomspace creation + creator membership, join request processing).

  6. Q: Why use Preload in admin handlers? A: To return related entities (creator/user/payer) in one logical query pipeline for display-ready API responses.

  7. Q: What is the risk of very verbose middleware logging? A: Sensitive data leakage and noisy logs; production should sanitize and control log levels.

  8. Q: Why is ban check done in middleware instead of each handler? A: Centralized enforcement guarantees banned users are blocked across all protected features.

  9. Q: What is the tradeoff of in-memory sessions? A: Simple and fast, but not shared across instances and lost on restart.

  10. Q: How to make sessions production-grade? A: Move to Redis/DB-backed sessions with TTL, horizontal scaling support, and revocation controls.

O. GORM + PostgreSQL advanced questions

  1. Q: Difference between First, Find, and Scan? A: First expects one row and can fail not-found, Find loads list/records, Scan maps custom selected projections.

  2. Q: Why use Count with model query builders? A: To support pagination metadata separate from paged data retrieval.

  3. Q: What is N+1 problem and where can it appear? A: Extra queries per row when loading relations lazily; mitigated using Preload.

  4. Q: Why connection pool tuning matters? A: Controls DB concurrency, prevents connection exhaustion, and stabilizes latency.

  5. Q: Why Supabase needs sslmode=require? A: Cloud Postgres endpoints require TLS-secured connections.

  6. Q: Why AutoMigrate order matters? A: Dependent tables need parent tables ready first to avoid relation/constraint issues.

  7. Q: Why store Firebase UID in users table? A: It is stable identity key that maps external auth to internal domain data.

  8. Q: Should every table have indexes? A: Only on high-selectivity/lookup columns (UIDs, foreign keys, status/date filters); over-indexing hurts writes.

  9. Q: What is soft delete in GORM? A: Mark row deleted via timestamp instead of hard deletion; allows recoverability and audit.

  10. Q: Why use WithContext(ctx) in DB calls? A: Propagates request cancellation/timeouts to DB operations.

P. Auth, session, and security hard questions

  1. Q: Why hybrid auth (Firebase + backend session)? A: Firebase handles identity proof; backend session simplifies domain authorization, cookie auth, and centralized ban/session invalidation.

  2. Q: Are cookies secure by default here? A: HttpOnly is used for session cookie, but production should enforce secure flags and strict environment config.

  3. Q: What happens if Firebase login succeeds but backend login fails? A: App treats it as authentication failure path and signs out/reset state to avoid partial login.

  4. Q: Why verify email for password users? A: Prevents unverified account misuse and improves trust/anti-abuse posture.

  5. Q: Is forgot-password handled by backend? A: No, current flow uses Firebase password reset email directly.

  6. Q: Why is admin ban-status endpoint risky if public? A: Potential user enumeration and moderation metadata exposure.

  7. Q: How would you secure admin endpoints? A: Add admin role middleware, protect routes under auth, and add audit logging/rate limits.

  8. Q: What is CSRF concern with cookie auth? A: Cookie-based auth can be CSRF-prone on web; mitigate with same-site policy/CSRF tokens depending on clients.

  9. Q: Why is session refresh endpoint useful? A: Extends active session safely without forcing frequent relogin.

  10. Q: What is least privilege in this system? A: Restrict route capabilities by user role/membership (roomspace/member/admin).

Q. Roomspace and collaboration edge cases

  1. Q: What if creator leaves roomspace? A: Ownership transfer logic promotes eligible member; if none remain, roomspace may be deleted.

  2. Q: How duplicate join requests are prevented? A: Service-level checks block duplicate pending requests and existing-member rejoin attempts.

  3. Q: How member removal is controlled? A: Only creator can remove others in current rule set; creator self-removal through dedicated leave flow.

  4. Q: Why validate roomspace membership middleware on read routes too? A: Prevents data leaks from unauthorized reads, not only writes.

  5. Q: Why pending join acceptance may not reflect instantly in app? A: Cache/state refresh timing; solve with refresh hooks/event-driven invalidation.

  6. Q: Should roomspace ID be UUID? A: Yes, UUID gives globally unique non-sequential IDs suitable for distributed systems.

  7. Q: What table stores roles? A: roomspace_members with role fields (creator, admin, member, etc.).

  8. Q: How invite code collision avoided? A: Generated code is checked against existing rows until unique.

  9. Q: Why active flag on membership? A: Supports logical leave/deactivation while retaining historical relationships.

  10. Q: What is tenancy boundary here? A: Roomspace acts as data partition boundary for shared-domain operations.

R. Expense, split, settlement, and recurring deep questions

  1. Q: Equal split precision issue handling? A: Floating division may produce decimals; UI/backend should use consistent rounding policy for display and settlement.

  2. Q: Why global net settlement preferred over pairwise in your use case? A: It reduces circular obligations and gives minimal-transfer final settlement.

  3. Q: How suggested settlement is computed conceptually? A: Debtors and creditors are matched by net amounts until all net balances resolve.

  4. Q: Why can dashboard show confusing owe/get-back simultaneously? A: If pairwise obligations are surfaced instead of net simplification.

  5. Q: Where recurring template and generated reminder differ? A: Template defines rule (frequency/members/payer config); notification is due-instance trigger to process action.

  6. Q: Does recurring auto-create expense always? A: Current behavior is user-driven notification processing flow unless explicit auto-generation path is enabled.

  7. Q: Why overdue may appear incorrectly? A: Date sync/state refresh mismatch between recurring detail source and expense-screen snapshot.

  8. Q: Why multi-payer support is important? A: Real shared expenses often have split payers; recurring edit/add must align with normal add-expense model.

  9. Q: What causes recurring notifications SQL type error (text = uuid)? A: Mismatched DB column types in query joins/filters; fix by schema alignment/casting correction.

  10. Q: Why reminder limit (429) UX message should be custom? A: Better user clarity: “Reminder limit reached for today” instead of generic failure.

S. Analytics, ML bridge, and fallback questions

  1. Q: Why summary can be 200 while predictions endpoint is 500? A: Summary has local DB fallback computations, but predictions/recommendations/anomalies depend on ML bridge availability.

  2. Q: What is graceful degradation in analytics? A: Show usable summary/trends and warnings when advanced ML endpoints fail.

  3. Q: Why have warnings in summary response? A: To expose partial degradation transparently (ML unavailable; using fallback).

  4. Q: How should frontend handle ML endpoint failures? A: Non-blocking UI with retry option and explanatory copy, not hard-crash or blank page.

  5. Q: Why separate ML bridge service? A: Decouples heavy model/runtime dependencies from core API service.

  6. Q: Is this classification or regression? A: Spending prediction and amount forecasting are regression-style outputs; anomaly/recommendation logic may combine heuristics + model outputs.

  7. Q: What if ML latency is high? A: Use timeout bounds, caching, async precompute, or queue-based inference.

  8. Q: Why trends endpoint still useful without ML? A: Historical aggregation alone provides strong analytical value.

  9. Q: What does “future projection unavailable” indicate? A: ML inference failed/timeouts/no model output for given inputs.

  10. Q: What is first production fix for analytics reliability? A: Add robust fallback contract and telemetry around ML bridge failures.

T. Notifications, permissions, and payment detection questions

  1. Q: Why need notification and SMS permissions? A: For payment auto-detection from app notifications and bank/payment SMS content.

  2. Q: Is permission requested at first launch? A: Yes via first-time permissions dialog flow.

  3. Q: Can app work without these permissions? A: Yes core manual expense features work; auto-detection capabilities degrade.

  4. Q: How avoid duplicate detected payments? A: Validation/dedupe logic checks recent transaction similarity/exact matches.

  5. Q: How to test payment detection safely? A: Use test notification pathways and inspect parser results/logs.

  6. Q: Why payment settings include app and merchant filters? A: To reduce false positives and user-noise.

  7. Q: Where detected payments are stored? A: payment_notifications table and related processing endpoints.

  8. Q: What if permissions revoked later? A: Feature should show disabled state and prompt user to re-enable permissions.

  9. Q: Why have processed flag for payment notifications? A: Supports queue-like lifecycle and avoids repeated handling.

  10. Q: What is biggest false-positive source? A: Ambiguous SMS formats and non-payment notification text patterns.

V. Deployment, DevOps, and reliability questions

  1. Q: What is your current runtime topology? A: Flutter app clients -> backend (local/Render) -> PostgreSQL (Supabase/local) + optional ML bridge service on Render.

  2. Q: Why did local login fail with connection refused? A: App pointed to LAN backend URL while server was unreachable/not running at that address.

  3. Q: Why Render login timed out at 30s? A: Cold start/slow backend response/network path; client timed out before response.

  4. Q: How to mitigate cold-start timeout? A: Increase initial login timeout, warm instances, optimize startup migrations, and use health checks.

  5. Q: Why SKIP_STARTUP_MIGRATIONS env exists? A: To avoid platform startup timeout penalties during boot on constrained hosting.

  6. Q: What logs are most useful in incidents? A: Request path/status, DB errors, timeout metrics, auth/session failures, and ML bridge error rates.

  7. Q: What should be environment-driven? A: Base URLs, DB URLs, secrets, payment keys, CORS origin allowlist, feature flags.

  8. Q: How do you do safe schema changes? A: Backward-compatible migrations first, deploy app/backend in compatible order, then cleanup.

  9. Q: Should admin APIs be internet-open? A: No; guard with auth/role checks and ideally network controls.

  10. Q: What is minimum production observability set? A: Structured logs, error tracking, latency percentiles, uptime checks, and alerting thresholds.
