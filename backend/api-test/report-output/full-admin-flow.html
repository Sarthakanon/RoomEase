RoomEase Full Admin Flow (A to Z)

Technical Summary Paragraph

The RoomEase admin subsystem is an operational oversight layer exposed through /api/admin/* endpoints. It provides system-level visibility (user/roomspace/expense/analytics aggregates) and moderation controls (ban/unban/check ban status). Ban enforcement is runtime-coupled with the global auth middleware: once a user is marked banned in PostgreSQL, protected API requests are denied and session invalidation is triggered. On the client, ban detection is handled through API interceptors plus periodic checks, then user logout and ban UI messaging are initiated.

Important current state: admin endpoints are currently public in routing and should be protected before production.

1. Backend files involved

  1. backend/main.go - Registers admin routes under /api/admin - Currently places these routes in public group (no auth middleware)

  2. backend/handlers/admin_handler.go - Implements all admin endpoints (stats, users, roomspaces, expenses, analytics, ban/unban)

  3. backend/middleware/auth.go - Not directly guarding admin routes right now, but enforces ban on protected APIs

  4. backend/models/user.go - Stores is_banned, ban_reason, banned_at

2. Admin API surface and behavior

2.1 System overview

  • GET /api/admin/stats
  • Returns:
  • total users
  • total roomspaces
  • total expenses
  • total expense amount
  • banned users count
  • last updated timestamp

2.2 User management

  • GET /api/admin/users
  • paginated list
  • optional search by name/email (ILIKE)
  • GET /api/admin/users/:userId
  • detailed user + roomspace count + expense count
  • POST /api/admin/users/:userId/ban
  • body includes reason
  • sets ban fields
  • POST /api/admin/users/:userId/unban
  • clears ban fields
  • GET /api/admin/users/:userId/ban-status
  • lightweight endpoint used by app-side monitoring

2.3 Roomspace oversight

  • GET /api/admin/roomspaces
  • paginated roomspace list
  • includes creator preload and active member count
  • GET /api/admin/roomspaces/:roomspaceId
  • roomspace detail + members + total/ count metrics

2.4 Expense oversight

  • GET /api/admin/expenses
  • paginated shared expenses with payer/roomspace preload
  • GET /api/admin/personal-expenses
  • paginated personal expenses with user preload

2.5 Admin analytics

  • GET /api/admin/analytics
  • Returns:
  • user growth by day (last 30 days)
  • category breakdown
  • subscription distribution
  • active roomspaces in last 7 days

3. Ban flow (end-to-end)

Step A: Admin bans a user

  1. Admin calls POST /api/admin/users/:userId/ban
  2. Handler finds user by firebase_uid
  3. Updates: - is_banned = true - ban_reason = <reason> - banned_at = now

Step B: User tries protected API

  1. Request hits AuthMiddleware
  2. Middleware validates session cookie
  3. Middleware calls checkUserBanStatus(userUID)
  4. If banned: - session deleted from session store - response 403 with banned/logout-required payload

Step C: Frontend reacts

  1. ApiService interceptors detect ban patterns (403, banned flags, error text)
  2. Ban monitoring/notification service triggers ban event
  3. UI shows ban dialog and user is signed out

This creates both proactive (polling) and reactive (interceptor) ban handling.

4. Frontend admin-related behavior (existing)

There is no full admin dashboard UI in the Flutter app by default. Current client-side admin integration mainly includes:

  1. Ban status check at login: - ApiService.login(...) -> _checkUserBanStatus(user.uid) - calls GET /api/admin/users/:userId/ban-status

  2. Periodic ban monitoring: - BanMonitoringService polls every ~30 seconds

  3. Ban UX: - BanListenerWidget + BanCountdownDialog - auto-logout and user messaging

So admin data display endpoints exist primarily backend-side (for admin panel, scripts, or API tools), while app currently consumes mostly ban-status path.

5. Database tables used in admin subsystem

  1. users - moderation fields (is_banned, ban_reason, banned_at) - admin list/search/detail source

  2. roomspaces - roomspace listing/detail and totals

  3. roomspace_members - member counts and roomspace user mapping

  4. expenses - system totals, admin expense list, roomspace expense metrics

  5. personal_expenses - admin personal expense listing

  6. subscription_payments / users.subscription_plan - subscription distribution and admin business visibility

  7. Other related support tables may be queried indirectly for aggregates depending on endpoint evolution.

6. Security posture and immediate hardening needed

Current risk: - main.go defines admin routes as public.

Recommended fixes: 1. Move /api/admin/* under protected group. 2. Add admin role/claim middleware (not just authenticated user). 3. Add audit log for admin actions (ban/unban/view sensitive records). 4. Apply pagination caps and stricter query validation. 5. Consider IP allowlist/rate limits for admin endpoints.

7. Supervisor-ready explanation of “how data is displayed”

Admin data display pipeline: 1. API request hits admin handler. 2. Handler runs paginated/aggregated GORM queries. 3. Preload is used for relational display fields (creator, payer, user). 4. Response is standardized JSON (success, data, optional pagination). 5. Consumer (admin panel/app/tool) renders tables/charts from this response.

8. One-line summary

Admin flow in RoomEase is API-driven moderation and observability: handlers read aggregated data from PostgreSQL via GORM, ban flags are enforced by auth middleware on protected APIs, and frontend ban monitoring ensures immediate user lockout experience.
