RoomEase Full Authentication Flow (Frontend + Backend)

This document explains exactly how authentication works in your current codebase.

Technical Summary Paragraph

RoomEase authentication is implemented as a federated identity plus server-session architecture: the Flutter client first authenticates with Firebase Authentication (Google OAuth or email/password) and obtains a Firebase ID token, then exchanges that token with the Go backend at /api/auth/login. The backend verifies the token with Firebase Admin SDK, upserts the user record in PostgreSQL by firebase_uid, and issues an HttpOnly session_id cookie backed by a server-side in-memory session store (24h TTL). From that point onward, protected API authorization is cookie/session driven via Gin middleware, which also enriches request context (user_id, email) and enforces ban checks from PostgreSQL. In short, Firebase performs identity proofing, PostgreSQL stores application user/domain state, and backend middleware enforces runtime access control for all authenticated operations.

1. High-level architecture

Your app uses hybrid auth:

  1. Firebase Authentication handles identity proof (Google sign-in, email/password sign-up/sign-in, forgot password email).
  2. Go backend verifies Firebase ID token and creates its own server session.
  3. App then uses cookie-based session auth (session_id) for all protected backend APIs.
  4. PostgreSQL stores user profile + domain data (roomspaces, expenses, etc.), and also user ban status.

Important: current backend auth is session cookie based, not JWT-based.

2. Frontend auth files and what each does

Core frontend auth files

  • lib/services/firebase_auth_service.dart
  • Wraps Firebase client SDK (firebase_auth) + Google SDK (google_sign_in).

  • Handles:

    • email signup
    • email login
    • Google login
    • send email verification
    • send password reset email
    • sign out

  • lib/features/auth/controllers/auth_controller.dart

  • Orchestrates app login/signup flow.
  • After Firebase login, fetches Firebase ID token and calls backend /api/auth/login.

  • For signup (email/password), does not login backend until user verifies email and logs in later.

  • lib/services/api_service.dart

  • HTTP client (dio) with cookie manager.
  • Calls backend login/logout/verify/refresh.

  • Persists cookie on device via PersistCookieJar.

  • lib/features/auth/presentation/login_screen.dart

  • Login UI.

  • Calls AuthController.loginWithEmail() / loginWithGoogle().

  • lib/features/auth/presentation/signup_screen.dart

  • Signup UI.

  • Creates Firebase account, sends email verification, then sends user back to login.

  • lib/features/auth/presentation/forgot_password_screen.dart

  • Calls Firebase reset email flow.

  • lib/widgets/auth_state_listener.dart

  • Watches Firebase auth state and routes user to login on sign-out.

3. Backend auth files and what each does (Go)

Core backend auth files

  • backend/main.go
  • Initializes Firebase Admin SDK + PostgreSQL + in-memory session store.
  • Registers routes.
  • Public route: POST /api/auth/login.

  • Protected routes use middleware.AuthMiddleware().

  • backend/handlers/auth.go

  • Login: verifies Firebase token, upserts user in Postgres, creates session, sets session_id cookie.
  • Logout: deletes session + clears cookie.
  • Verify: checks session validity from middleware context.

  • Refresh: extends session expiry.

  • backend/services/firebase.go

  • VerifyToken(idToken) via Firebase Admin (VerifyIDToken).

  • Extracts UID, email, name claims.

  • backend/middleware/auth.go

  • Reads session_id cookie.
  • Validates session from session store.
  • Loads ban status (from Postgres) and blocks banned users.

  • Sets context values: user_id, email, session_id.

  • backend/services/session.go

  • In-memory session store (map + mutex).
  • Generates random session IDs (32 bytes -> 64 hex chars).

  • 24h session TTL support + cleanup goroutine.

  • backend/models/session.go

  • Session model (id, user_id, email, created_at, expires_at).

  • backend/services/postgres.go

  • User lookup/creation (GetUserByFirebaseUID, CreateUser, etc.).

  • backend/config/firebase.go

  • Initializes Firebase Admin credentials (env JSON/env fields/file fallback).

4. Exact login flow (Google)

  1. User taps Google login in login_screen.dart.
  2. AuthController.loginWithGoogle() calls FirebaseAuthService.signInWithGoogle().
  3. Firebase SDK signs in user locally and returns Firebase user.
  4. App calls user.getIdToken().
  5. App sends token to backend: - POST /api/auth/login - body: { "firebase_token": "<Firebase ID Token>" }
  6. Backend AuthHandler.Login: - verifies token with Firebase Admin (services.VerifyToken). - finds or creates user in Postgres by firebase_uid. - creates server session with 24h expiry. - sets HttpOnly cookie session_id.
  7. App stores cookie via Dio cookie manager.
  8. Further API calls are authenticated via cookie.

5. Exact login flow (email/password)

  1. User signs in using Firebase email/password (FirebaseAuthService.signInWithEmailAndPassword).
  2. App enforces emailVerified == true; otherwise signs out and blocks login.
  3. If verified, app gets Firebase ID token.
  4. App calls backend /api/auth/login same as Google flow.
  5. Backend verifies token, creates session cookie.

6. Token/JWT details (what is actually used)

  • Sent from app to backend once at login:
  • Firebase ID token (JWT issued by Firebase).
  • Used for backend session after login:
  • session_id cookie (opaque random token, server-side session store).
  • For protected APIs:
  • Cookie auth (session_id) only.

So in your current implementation: - Firebase JWT is used for initial authentication proof. - App/backend then switch to cookie session model. - Backend is not issuing its own JWT for API auth.

Note: github.com/golang-jwt/jwt/v4 appears in go.mod as indirect dependency but not used in this main auth flow.

7. How verification is done

Firebase verification

  • Backend calls Firebase Admin VerifyIDToken in backend/services/firebase.go.
  • If invalid/expired => backend returns 401.

Session verification

  • Every protected route passes through backend/middleware/auth.go.
  • Middleware checks session_id cookie in session store.
  • If missing/invalid/expired => 401.

Ban verification

  • Middleware also checks user ban flags in Postgres (models.User via config.DB).
  • If banned => 403 and forces logout behavior client-side.

8. Is PostgreSQL included in login? What is its role?

Yes, PostgreSQL is part of login flow.

During /api/auth/login: - Backend checks if user exists by firebase_uid. - If not exists, creates user row. - If exists, may sync name from Firebase.

PostgreSQL roles in auth ecosystem: - stores app user records and metadata - stores ban/suspension flags - stores all business-domain data (roomspaces/expenses/etc.)

PostgreSQL is not verifying password or Google OAuth directly; Firebase does that.

9. Create account flow

Current create-account path uses Firebase email/password.

  1. SignupScreen -> AuthController.signUpWithEmail(...).
  2. FirebaseAuthService.signUpWithEmailAndPassword(...): - creates Firebase user - sets display name - sends email verification
  3. Controller creates Firestore user doc (marked as non-critical/backward compatibility).
  4. User is asked to verify email and then login.
  5. Backend session is not created at signup time; created on actual login.

10. Forgot password flow

ForgotPasswordScreen calls: - FirebaseAuthService.sendPasswordResetEmail(email) - internally FirebaseAuth.sendPasswordResetEmail

This is handled by Firebase directly (email reset link workflow). No backend password reset API is used in this flow.

10.1 Change password flow (from Settings)

Change password is implemented on the Firebase side and is triggered from Settings UI.

Frontend flow: 1. SettingsScreen._showChangePasswordDialog() 2. FirebaseAuthService.changePassword(currentPassword, newPassword) 3. Internally: - EmailAuthProvider.credential(email, currentPassword) - user.reauthenticateWithCredential(...) - user.updatePassword(newPassword)

Important behavior: - This flow works only for users with email/password credentials. - For Google-only accounts, password change is not managed by your backend; identity/provider policy is handled by Firebase/Google. - No /api/auth/change-password endpoint is used in current backend.

12. Key observations / caveats in current implementation

  1. Backend sessions are in-memory (NewInMemorySessionStore). - Sessions are lost on backend restart/redeploy.
  2. Cookie in auth.go currently sets secure=false. - Should be true in production HTTPS-only environments.
  3. Admin routes in main.go are currently public (comment says add admin auth later).
  4. Firebase is source of identity; Postgres is source of app data and authorization context.

13. Exact Frontend-to-Backend Method Mapping (Auth)

Frontend method call chain for auth:

  1. Google login: - LoginScreen._googleLogin() - AuthController.loginWithGoogle() - FirebaseAuthService.signInWithGoogle() - User.getIdToken() - ApiService.login(idToken) -> POST /api/auth/login

  2. Email login: - LoginScreen._login() - AuthController.loginWithEmail(email, password) - FirebaseAuthService.signInWithEmailAndPassword(...) - User.getIdToken() - ApiService.login(idToken) -> POST /api/auth/login

  3. Logout: - AuthController.logout() - ApiService.logout() -> POST /api/auth/logout - FirebaseAuthService.signOut()

  4. Session verify/refresh: - ApiService.verifySession() -> GET /api/auth/verify - ApiService.refreshSession() -> POST /api/auth/refresh

  5. Forgot password: - ForgotPasswordScreen submit - FirebaseAuthService.sendPasswordResetEmail(email) - Firebase sends reset email directly

  6. Change password (settings): - SettingsScreen._showChangePasswordDialog() - FirebaseAuthService.changePassword(currentPassword, newPassword) - EmailAuthProvider.credential(...) + reauthenticateWithCredential(...) + updatePassword(...)

Backend auth handlers serving above: - AuthHandler.Login (backend/handlers/auth.go) - AuthHandler.Logout (backend/handlers/auth.go) - AuthHandler.Verify (backend/handlers/auth.go) - AuthHandler.Refresh (backend/handlers/auth.go)

Token/session bridge used for frontend-backend connection: - Request body field: firebase_token (Firebase ID token JWT) - Response/session mechanism: session_id HttpOnly cookie - Subsequent API auth: cookie-based via AuthMiddleware

14. One-line summary

RoomEase auth = Firebase identity token at login -> backend verifies with Firebase Admin -> backend creates cookie session (session_id) -> all protected APIs use session middleware + Postgres checks.

15. Database Tables Used (Auth)

Tables used directly in auth flow:

  1. users - Purpose: - maps Firebase identity (firebase_uid) to app user profile - stores email/name and account-level flags (is_banned, ban_reason, etc.) - Used by: - AuthHandler.Login for find-or-create user behavior - AuthMiddleware ban check path

  2. session storage (not a DB table in current implementation) - Current state: - backend sessions are in-memory (InMemorySessionStore) - cookie session_id points to memory map entry - Operational implication: - sessions are cleared on backend restart/redeploy
