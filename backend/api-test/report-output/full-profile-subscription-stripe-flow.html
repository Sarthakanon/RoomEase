RoomEase Profile + Subscription + Stripe Flow

Technical Summary Paragraph

Profile and subscription in RoomEase are implemented as authenticated account-domain services on top of Firebase identity and backend session authorization. Profile data is read/written through /api/user/profile, with frontend caching, optimistic UI refresh, and auxiliary Cloudinary uploads for QR/profile assets. Subscription status is primarily persisted in the users table (subscription_plan, subscription_expiry) and managed via subscription endpoints plus payment verification endpoints. Stripe is integrated as a payment-intent verification layer, while final subscription state transitions are handled by backend subscription/payment handlers. The architecture is functional but currently mixes test-oriented Stripe setup and eSewa-oriented verification paths, so production hardening is still needed.

1. Profile system flow

Backend

Handler: backend/handlers/user.go - GetProfile -> GET /api/user/profile - UpdateProfile -> PUT /api/user/profile

Data source: - PostgresService.GetUserByFirebaseUID(...) - PostgresService.UpdateUser(...)

Frontend

Main screen: - lib/features/profile/presentation/profile_screen.dart

Load flow: 1. Reads Firebase current user for baseline name/email/photo. 2. Calls SmartApiService.getUserProfile() to override with backend profile fields. 3. Caches profile data locally for faster tab switching.

Update flow: 1. User edits name/phone/QR. 2. Calls SmartApiService.updateUserProfile(...). 3. For photo/QR image upload, uploads file first then updates profile URL. 4. Forces state refresh for dependent screens and emits realtime profile update event.

2. Profile database tables

  1. users - columns used in profile context: - firebase_uid - email - name - phone - qr_image_url - is_banned, ban_reason, banned_at - subscription_plan, subscription_expiry

No separate profile table exists; profile is user-row driven.

3. Subscription domain flow

Backend endpoints

Handler: backend/handlers/subscription_handler.go

  • GET /api/subscription/current
  • derives current plan/status from users table

  • auto-downgrades expired plans to free

  • POST /api/subscription/cancel

  • marks expiry end-of-period behavior

  • POST /api/subscription/reactivate

  • clears expiry for reactivation

  • GET /api/subscription/history

  • reads subscription_payments records

Frontend

  • SubscriptionProvider (lib/features/subscription/providers/subscription_provider.dart)
  • SubscriptionService (lib/features/subscription/services/subscription_service.dart)

Behavior: - Initializes with safe default free plan. - Attempts backend sync; gracefully falls back if API/path fails. - Computes roomspace entitlement limits from active plan. - Supports upgrade/cancel/reactivate/history flows.

4. Stripe setup and payment flow (current implementation)

Frontend Stripe package

  • flutter_stripe via lib/services/stripe_payment_service.dart

Client flow: 1. call backend create intent endpoint (/api/payment/stripe/create-intent) 2. initialize Stripe payment sheet with client secret 3. present payment sheet 4. on success call subscription verification/update flow in app logic

Backend Stripe handler

  • backend/handlers/stripe_handler.go

Endpoints: - POST /api/payment/stripe/create-intent - POST /api/payment/stripe/verify - POST /api/payment/stripe/subscription/verify

Important current state: 1. Stripe secret key is hardcoded in code (test key) in handler init. 2. Subscription verify endpoint verifies payment intent success, but comment notes final subscription activation should be done by main backend flow. 3. Frontend currently chains Stripe verification then calls subscription verify endpoint that follows existing payment-record path.

5. eSewa coexistence

Subscription and settlement payment verification also exists via eSewa handlers: - backend/handlers/esewa_handler.go

So payment stack is mixed-mode: - Stripe payment intent path - eSewa verification path

The frontend subscription service currently supports both, with Stripe as one branch.

6. Exact frontend-to-backend method mapping

Profile mapping

  1. Load profile: - ProfileScreen._loadProfileData() - SmartApiService.getUserProfile() - ApiService.get('/api/user/profile')

  2. Update profile: - ProfileScreen._saveProfile() - SmartApiService.updateUserProfile(...) - ApiService.updateUserProfile(...) - PUT /api/user/profile

  3. Upload QR/profile photo: - upload file (Cloudinary service) - update URL via profile update API

Subscription mapping

  1. Current subscription: - SubscriptionService.getCurrentSubscription() - ApiService.get('/api/subscription/current')

  2. Cancel: - SubscriptionService.cancelSubscription() - ApiService.post('/api/subscription/cancel')

  3. Reactivate: - SubscriptionService.reactivateSubscription() - ApiService.post('/api/subscription/reactivate')

  4. History: - SubscriptionService.getSubscriptionHistory() - ApiService.get('/api/subscription/history')

  5. Stripe create intent: - StripePaymentService._createPaymentIntent() - ApiService.post('/api/payment/stripe/create-intent')

  6. Stripe subscription verification path: - SubscriptionService.processPayment(method='stripe') - ApiService.post('/api/payment/stripe/subscription/verify') - then update path via ApiService.post('/api/payments/subscription/verify')

7. Database tables used (profile/subscription/payment)

Primary tables: 1. users - profile fields, ban state, current subscription plan/expiry

  1. subscription_payments - subscription transaction history

  2. balance_settlements - settlement payment records (roommate settlement payments)

Related cross-feature tables: 4. notifications (payment reminders, system notifications) 5. roomspace_members (plan-driven roomspace usage checks rely on roomspace count) 6. roomspaces (usage count for plan limits)

8. Implementation notes / hardening points

  1. Stripe key management should move to secure env vars (not hardcoded).
  2. Stripe webhook-based confirmation is not the main path in this code; verification is request-driven.
  3. Subscription provider intentionally falls back to free defaults when APIs fail, which can hide backend issues from users.
  4. Plan-limit enforcement is partly computed frontend-side; authoritative server checks should remain enforced.

9. One-line summary

Profile is user-row centric and session-protected, while subscription is plan-state persisted on users plus payment-history tables, with Stripe/eSewa verification flows bridging payment completion to subscription state updates.
