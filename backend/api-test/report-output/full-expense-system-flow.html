RoomEase Full Expense System Flow (A to Z)

Technical Summary Paragraph

The RoomEase expense system is a roomspace-scoped financial ledger pipeline where expense creation, split attribution, balance computation, settlements, recurring automation, and dashboard rendering are connected through a shared API/cache/event architecture. On the client, dashboard and expense pages submit typed payloads through SmartApiService/ApiService, while split validation happens both in UI utilities and backend handlers for integrity. On the server, expense records (expenses) and participant shares (expense_splits) are persisted transactionally, then consumed by balance logic that computes net positions from payer-credit minus split-debit with settlement reconciliation. Recurring templates run through a scheduler/notification workflow (cron + recurring service), generating reminders and optionally materializing expenses. Overall, this is a stateful, database-driven domain model with roomspace membership authorization at every shared boundary.

1. Dashboard -> Add Expense integration (exact flow)

Frontend call chain

  1. User opens add expense from dashboard: - MobileDashboard opens AddExpenseDialog (lib/features/home/widgets/add_expense_dialog.dart)

  2. Form preparation and validation in dialog: - title/amount/category/roommates/payers/split type/custom splits/recurring config - validates payer total equals amount - validates split data with: - ExpenseCalculationUtils.validateSplitData(...)

  3. Submit path: - dialog emits ExpenseData via onSubmit - dashboard builds API request (ExpenseCreateRequest/JSON) - SmartApiService.createExpense(expenseData) - online/offline service integration - backend call eventually hits ApiService.createExpense(...) -> POST /api/expenses

  4. Post-submit refresh: - dashboard/balances/expense caches invalidated - realtime event trigger (notifyExpenseCreated) updates dependent views

2. OCR receipt scanning (how it works)

File

  • lib/services/ocr_service.dart

Packages used

  • google_mlkit_text_recognition
  • image_picker
  • permission_handler

OCR pipeline

  1. Request camera/gallery permission.
  2. Pick image from camera/gallery.
  3. Convert file to ML Kit input image.
  4. Run text recognizer (TextRecognizer.processImage).
  5. Parse extracted text using regex heuristics: - likely total amount - candidate merchant name - date - all amount-like values
  6. Return OcrScanResult to UI (ReceiptScannerDialog / add expense flow).

Notes: - OCR extraction is heuristic-based, not guaranteed exact; user can edit before submit.

3. Expense creation/splitting backend logic

Handler

  • backend/handlers/expense.go

Key backend checks (CreateExpense)

  1. Auth required (user_id from middleware).
  2. Request validation (CreateExpenseRequest).
  3. Membership validation for roomspace.
  4. Payer validation (paid_by must be member; default = auth user).
  5. Split validation (validateExpenseRequest) by split type: - EQUAL - PERCENTAGE (must sum exactly 100) - EXACT (must sum exactly expense amount)
  6. Split calculation (calculateSplits): - equal split includes payer in participant set if missing - percentage/exact uses provided custom map
  7. Persist expense + splits using DB service transaction.
  8. Optional recurring-template creation if recurring config exists.
  9. Notifications to affected roommates.

Persist layer

  • PostgresService.CreateExpense(...) creates expenses then expense_splits in transaction.

4. Balance calculation and settlement logic

Core service

  • backend/services/balance_service.go

Roomspace balance algorithm

For each expense: 1. Credit full amount to payer balance. 2. Debit each participant by split share. 3. Uses normalizedSharesByUser(...) to prevent split duplication/corruption from inflating totals.

After expenses: 4. Apply settlements: - payer of settlement (from_user) gets balance increase - receiver (to_user) gets balance decrease

Output: - BalanceSummary (total_expenses, user_balances, member list, etc.)

API surface

  • GET /api/roomspaces/:id/balances
  • GET /api/roomspaces/:id/balances/:userId
  • POST /api/roomspaces/:id/settlements
  • GET /api/roomspaces/:id/settlements
  • GET /api/roomspaces/:id/settlements/suggestions
  • POST /api/roomspaces/:id/balances/refresh

Current mode

  • response indicates balance_mode: global_net
  • primary values surfaced as:
  • you_owe
  • you_are_owed
  • your_balance

6. Recurring payments system (template + notification + action)

Models

  • RecurringExpenseTemplate (recurring_expense_templates)
  • RecurringExpenseNotification (recurring_expense_notifications)
  • RecurringConfig (is_recurring, interval, start/end, notify flags)

Scheduling logic

Backend service: - backend/services/recurring_expense_service.go

Scheduler: - backend/services/cron_service.go - jobs: - recurring processing hourly (0 * * * *) - cleanup old processed notifications daily (0 2 * * *)

“Notify before one day” behavior

In model method: - RecurringExpenseTemplate.ShouldSendNotification(currentDate)

Logic: 1. compute next scheduled date from interval + last_generated/created_at 2. compute notificationDate = nextDate - notification_days_before 3. compare date-only (day precision) and notify exactly on that day

So if notification_days_before = 1, reminder is generated on previous day.

Notification processing actions

Endpoint: - POST /api/recurring-expenses/notifications/:notification_id/process

Actions supported: - create_now (generate expense now) - schedule_later - skip_once - cancel (deactivate template)

Also supports soft-delete/restore template window (24h undo).

7. Personal expense vs shared expense

Shared expenses: - require roomspace membership - use splits and affect balances

Personal expenses: - user-private only - endpoints: - POST /api/personal-expenses - GET /api/personal-expenses - DELETE /api/personal-expenses/:id - do not affect roomspace balances

9. Database tables used and purpose (Expense System)

Core expense ledger: 1. expenses - shared expense header rows (roomspace_id, amount, paid_by, split_type, etc.)

  1. expense_splits - participant-level owed share rows per expense

  2. personal_expenses - private user expense ledger

Balance & settlement: 4. user_balances - cached computed balances per user+roomspace

  1. settlements - payment settlement records between users

Recurring subsystem: 6. recurring_expense_templates - recurring template definition and recurrence config

  1. recurring_expense_notifications - reminder/action queue rows for upcoming recurring payments

History and governance: 8. expense_history - created/edited/deleted audit-style history

  1. expense_deletion_requests - deletion approval workflow request header

  2. expense_deletion_approvals - per-user approvals/rejections for deletion requests

Notification context: 11. notifications - cross-feature user notification inbox (expense/join/reminder/etc.)

Identity/membership dependency tables used for authorization and names: 12. users 13. roomspaces 14. roomspace_members

10. One-line summary

Expense system = validated split entry -> transactional persistence -> normalized net balance computation + settlement reconciliation -> recurring reminder/generation workflow -> dashboard/pages rendered from roomspace-scoped APIs and cache-aware frontend services.
